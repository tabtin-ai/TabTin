# 写入与验证

仅在已经得到 `confirmed_plan` 或 `flat_exemption=true`，并且已有完整 `reuse_plan`（见 [reuse-plan.md](reuse-plan.md)）后读取本文。

## 写入顺序

1. 遵守已确认的 `reuse_plan`：`reuse` / `reuse_specified` 只写对应表；`create_new` 先 `table create` 并把新 ID 记入 `task_created_table_ids`。若仍需扫表核对字段/关联，可用 `table list`、`table info`，但不得绕过 `reuse_plan` 向未授权的历史表写行，也不得在未确认时把历史表当默认写入目标。避免重复创建双向关联。
2. 先创建被其他表引用的表，再创建依赖它的主实体表或明细表。
3. 用 `table link create` 创建关联；默认由系统处理双向字段，不手工再建一列对称关联。
4. 可复用对象和主实体有稳定键时，使用批量 `record upsert --records ... --upsert-on`。
5. upsert 后分页读取记录，建立“业务键 → record_id”索引；不要假设 upsert 回执一定包含完整 ID 映射。
6. 批量写入明细并携带 `task_id`。关联字段写 `[{"id":"record_id"}]`，多对多写数组。
7. 需要补关联时使用批量 update 或 `table link set`。关联显示名应来自目标记录主显字段，不能显示裸 UUID。

多行新增优先 `record bulk-insert` 或 `table import`；按业务键合并用 `record upsert`；已有不同 `record_id` 的差异化修改用批量 `record update --records`；同值批改用 `record update-by-filter`。单次批量上限以 CLI 帮助为准，超限分页。

## 明细批次快照

明细默认表达“本次任务看到的全集”。同一 `task_id` 重跑时：

1. 查询带该 `task_id` 的旧明细并收集 `record_id`。
2. 批量删除本批旧明细。
3. 批量写入本批新全集。
4. 验证本批明细数等于当前输入应写入数。

只有用户明确要求“按明细业务键长期合并”时才改用 upsert；即便如此，也要处理本批范围内已经消失的旧明细。

## 验收断言

仅检查本次方案实际存在的角色：

| 断言 | 通过条件 | 失败后的定向补救 |
|---|---|---|
| 主实体数量 | 主实体行数不少于本次应写数 | 补批量 upsert 或 bulk-insert |
| 明细数量 | 有明细方案时至少一行；部分数据必须如实标记 | 补采或补写缺失明细 |
| 可复用对象 | 对象表有记录，引用侧存在 link 字段 | 先补对象、重建 ID 索引、再补关联 |
| 关联一致 | 抽样主实体的关联数与明细侧引用数一致 | 以明细侧为准批量修复关联 |
| 关联可读 | link title 非空且不是裸 UUID | 依据目标表主显字段补 title |
| 快照一致 | 同 `task_id` 的明细数等于本批应写数 | 清除本批旧行后重写全集 |

单表豁免只检查主表实际行数与预期写入数，并确认没有错误创建关联表。

## 复用违规

- 发现工具轨迹在复用门闩完成前出现写表命令：停止写入，补一次复用确认卡。
- 用户指定的表不可用：说明原因，回到确认意图（其他 / 全部新建），禁止静默改写别的历史表。

## 失败处理

- 任一适用断言失败时，禁止进入最终复盘。
- 只针对失败断言补救一轮，然后重新执行该断言及受影响的下游断言。
- 补救后仍失败时停止自动修改，向用户说明失败项、已经尝试的补救以及可选降级方案。
- 未经用户明确要求，不因验收失败而整表删除重建，也不重新运行整条采集链。
